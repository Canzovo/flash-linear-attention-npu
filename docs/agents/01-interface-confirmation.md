# 接口确认

本阶段把用户提供的标杆和需求收敛为可评审的接口契约。新接口只有在用户确认数学语义、输入输出和支持边界后，才能进入 CPU 标杆生成。

## 输入门禁

用户至少提供一种可定位版本的标杆：

- 参考实现代码或固定 commit 的链接。
- 已发布接口文档、schema 或 API 定义。
- 能表达输入、输出和属性语义的测试或可运行示例。
- 论文或公式可以作为补充，但不能单独替代工程标杆。

同时确认标杆的来源、版本、许可证约束、预期支持范围和目标调用入口。缺少标杆、版本不明确或无法判断哪份材料权威时，先列出缺失项并请求用户补充，不进入实现。

## 分析用户标杆

按以下顺序建立证据链：

1. 公开接口、文档和用户明确说明决定对外契约。
2. 标杆测试和示例补充边界、默认值及异常行为。
3. 标杆实现用于还原公式、计算顺序、状态传播和数值细节。
4. 论文或相邻实现只用于解释和交叉验证，不覆盖用户确认的契约。

不同材料不一致时，记录“材料、差异、候选解释、影响”，由用户确认采用哪一种语义。不得自行选择最容易实现的版本。

## 接口契约

接口确认记录至少包含：

| 项目 | 需要确认的内容 |
| --- | --- |
| 接口身份 | 算子名、公开入口、L2/L0/aclnn/Python 层级和版本 |
| 输入 | 名称、顺序、required/optional、shape、dtype、format、layout、device 和语义 |
| 属性 | 名称、类型、默认值、取值范围、是否可由 descriptor 或已有信息推导 |
| 输出 | 数量、顺序、shape、dtype、layout、状态输出和别名关系 |
| 数学语义 | 公式、计算顺序、归一化、缩放、mask、状态更新和返回值语义 |
| 边界行为 | 空输入、partial chunk、padding、无效区、极端值和不支持组合 |
| 错误行为 | host 校验、错误类型、返回码和报错条件 |
| 支持范围 | SoC、fixed/varlen、head 关系、K/V/chunk 维度和功能非目标 |
| 性能目标 | 目标 shape、基线、目标指标和允许的 correctness fallback |

对预留但暂不支持的参数，明确其公开形态、host 拦截和未来兼容策略。不能验证的能力不得宣称支持。

## 接口与 ABI 约束

- 优先复用已有接口信息，不把可由 tensor descriptor、InferShape、host tiling、tiling data 或 workspace 推导的信息新增为参数。
- op_host、InferShape、tiling、kernel、op_api、schema、Python wrapper、公开文档和测试中的名称、顺序、类型及默认值必须一致。
- 已发布接口或 ABI 的变更按根 `AGENTS.md` 的强制红线执行；需要评审的变更在取得确认前不得进入开发。
- 同一算子在所有支持 SoC 上保持同一公开接口和 L0 原型，平台差异留在实现内部。

## 阶段输出

提交给用户确认的内容应简洁、可逐项判断：

1. 标杆来源和固定版本。
2. 接口签名与逐参数说明。
3. 数学语义和状态语义。
4. 支持矩阵、性能目标和明确非目标。
5. 边界、异常及兼容性规则。
6. 尚未解决的问题和需要用户选择的差异。

只有接口和语义获得用户确认，且没有阻塞性歧义，才进入 [`02-reference-generation.md`](02-reference-generation.md)。
