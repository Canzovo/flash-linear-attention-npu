# 算子测试

本阶段以已确认接口、CPU 标杆和算子设计为依据，证明当前实现的功能、精度、边界、确定性、内存和性能符合交付要求。具体构建、安装和 ATK 命令分别以 `docs/开发者指南.md`、`tests/atk/README.md` 和当前算子的 ATK README 为准。

## 阶段输入

- 已确认的接口契约、支持范围和异常行为。
- 已完成参考实现对齐或用户验收的独立 CPU 标杆、输入生成和比较标准。
- 评审通过的设计、可达 TilingKey、风险和验证计划。
- 当前实现、目标分支 diff 和受影响文件列表。
- 特性修改任务还需要确认的差异清单、修改前行为和既有场景回归范围。
- 优化任务还需要优化前性能基线、profiling 方法、目标 shape 和预期收益。

CPU 标杆提供精度预期结果，但不能替代接口、边界、确定性、内存、性能和端到端验证。

## 验证原则

- 按改动风险选择验证范围，不把“能编译”当作“功能正确”。
- 测试覆盖语义路径、调度路径和值域路径，不只覆盖默认 shape。
- 当前代码、当前测试资产、当前 CPU 标杆和当前构建产物必须对应，不能复用旧包或旧输出形成结论。
- 已执行、未执行和失败的验证分别记录；未执行项必须说明原因、影响和剩余风险。
- 仓内 ATK 自测试与 GitHub NPU CI 是独立门禁，不能互相替代。

## 从改动确定测试范围

开始验证前，以目标分支与当前 `HEAD` 的 diff 列出受影响文件，再按下表确定最低测试范围。

| 改动类型 | 最低验证范围 |
| --- | --- |
| 文档-only | 格式、相对链接、命令与当前脚本、文档与代码语义一致性 |
| 测试或 CPU 标杆-only | 语法/导入、CPU 标杆对齐或验收，并实际执行被修改的测试入口 |
| 算子特性修改 | 新增或变化场景的精度、边界和异常验证，以及未受影响既有场景的回归测试 |
| 算子私有 op_host、tiling、kernel、op_api 或 wrapper | 当前算子的构建、CPU 标杆精度和对应边界/反向场景 |
| TilingKey、模板选择或运行时分支 | 全部可达 key、普通/边界 case 和实际命中证据 |
| 性能策略、流水或资源规划 | 精度、确定性、内存检查、目标性能和泛化性能 |
| 公共组件、ABI、代码生成模板或 runtime | 所有受影响算子的对应测试，以及共享路径专项测试 |
| 公开接口、打包或安装行为 | ABI、公开入口、重复安装、OPP 内容和必要 Example/ST |
| GDN 端到端链路 | 受影响单算子测试和 Example/ST |

无法可靠映射公共改动的影响范围时，应继续分析引用、生成和调用关系并显式报告，不能静默跳过。

## 测试契约与资产

已有 ATK 工程的算子应同步维护：

- 算子 ATK README 和能力覆盖矩阵。
- `<op>.yaml` 和 `gen_<op>.py`。
- 已评审的 `atk_<op>.json`。
- `executor_<op>.py` 及其 CPU 标杆调用。
- 性能、确定性、mssanitizer 用例和 TilingKey 覆盖矩阵。

新增算子没有 ATK 工程时，应在交付前补齐上述资产。CPU 标杆的接口、输入生成、比较范围和阈值依据要能在测试资产中追溯；工具、目录和参数说明只在 `tests/atk/README.md` 维护。

## 自测试闭环

### 1. 快速开发迭代

1. 确认当前 CPU 标杆版本；仅在 `02` 已确认需要变化时更新 CPU 标杆，并同步必要用例和覆盖矩阵。
2. 先运行 CPU 标杆自身测试；存在 GPU 或 Triton Ascend 参考实现时，确认代表性 case 仍然对齐；用户直接提供 CPU 标杆时，确认其验收用例仍然通过。
3. 按目标 SoC 构建并安装当前代码，确认运行时命中本轮产物。
4. 对每个受影响算子执行 ATK 精度测试。
5. 当前代码、CPU 标杆、测试用例和构建产物全部通过，才算一次有效迭代。

精度未通过时先定位根因，不使用该版本的性能数据推进优化结论。

### 2. 轮次验收

选定一个精度通过版本后，固定代码、CPU 标杆、测试资产和构建产物：

1. 运行 ATK `all`，完成精度、确定性和 mssanitizer。
2. 性能相关改动单独运行 `performance`，记录目标锚点和相对基线变化。
3. 按风险补充 ctypes ABI、公开入口、多卡、autograd、Example/ST、多 SoC 和 NPU CI。
4. 检查没有测试输出、profiling、日志、缓存或生成物进入提交。

## 特性修改验收

- 对每个确认的特性差异增加正向、边界和必要反向 case，并验证接口、输出和异常行为符合新契约。
- 对差异清单中保持不变的接口、CPU 标杆结果和既有支持场景执行回归，证明修改没有破坏兼容性。
- 修改公共组件、ABI、生成模板或 runtime 时，逐一测试全部受影响算子。
- 测试发现实现需要改变未确认语义或支持范围时返回 `01`；发现 CPU 标杆或预期结果需要变化时返回 `02`，不得在测试中临时修改标准。

## 优化回归

优化版本只有在功能和精度保持不变后，才能形成性能结论：

- 使用同一目标 SoC、shape、输入、构建方式、profiling 方法和统计口径比较优化前后结果。
- 先完成 CPU 标杆精度、边界、确定性和内存检查，再记录性能数据。
- 除目标 shape 外，覆盖设计中的泛化矩阵、全部受影响 TilingKey 和支持 SoC，确认没有用局部收益换取功能或性能退化。
- 对 workspace、同步、stage 或流水改动，补充连续多 task、slot 复用、tail、varlen 和空任务等相关场景。
- 报告目标性能、泛化性能、资源变化和相对基线差异；未达到预期时如实记录，不调整基线或比较口径。
- 若测试发现公开接口、数学语义、支持范围或 CPU 标杆必须改变，停止优化验收并重新归类任务。

## 测试矩阵

按接口契约和设计选择适用维度：

- fixed length 和 varlen；varlen 覆盖短序列、尾 chunk、多 chunk 及关联元数据。
- 一一对应和 grouped/GVA head 关系；至少覆盖 head ratio 为 1 和大于 1。
- 关键 `chunkSize`、K/V 维度、主 dtype、辅助输入 dtype 和 layout。
- 可选输入存在/缺失、初始/最终状态和预留但不支持参数。
- 普通块、边界块、partial chunk、padding、无效区和极端值域。
- 单 task 与同一 core 连续多 task，触发 workspace slot 复用和同步协议。
- 目标 SoC 以及公共逻辑涉及的其他支持 SoC。

正向 case 的预期结果来自 CPU 标杆。反向和异常 case 要验证接口契约规定的明确拦截，不以 kernel 崩溃或未定义结果作为通过。

## TilingKey 覆盖

新增或修改 TilingKey、模板选择条件或 tiling 分支时，从 host tiling、模板注册和 kernel 分派代码枚举全部可达 key。当前算子的 ATK README 应维护：

| TilingKey | 选择条件 | 普通 case | 边界 case | 目标 SoC | 实际命中证据 |
| --- | --- | --- | --- | --- | --- |
| `<key>` | dtype、layout、shape、属性和平台条件 | ATK case | ATK case | A2/A3/A5 | host tiling UT 或运行时记录 |

每个可达 key 需要普通和边界 case，同一 key 内的运行时分支也要覆盖。输入 shape 只能说明预期选择；实际命中必须由 host tiling UT 或运行时证据确认。明确不支持的组合要有 host 校验和反向用例。

## 失败定位

- 固定行、chunk、head 的块状错位，整片符号/幅值异常或维度映射错误：优先检查索引、layout、任务分配、搬运和写回。
- 误差集中在 padding 或无效区：核对接口契约、CPU 标杆和测试屏蔽范围。
- 同一输入多次结果不一致：优先检查 workspace 重叠、pipe event、cross-core flag 和生命周期。
- 随机数值误差：固定 shape、layout、属性和结构数据后进行多轮复检，再判断是否稳定劣于用户提供的参考实现或 CPU 标杆。
- CPU 标杆与用户提供的参考实现不一致：返回标杆生成阶段，不能修改 NPU 实现来迁就错误的预期结果。

不得通过缩小输入范围、删除失败 case、降低覆盖强度或放宽阈值制造通过结论。

## 结果记录与退出门禁

测试结论至少包含：

- 受影响算子和选择该范围的依据。
- CPU 标杆版本、参考实现对齐或用户验收状态，以及测试资产版本。
- 目标 SoC、测试层级、执行项和结果。
- 精度用例总数、失败数和必要的错误分类。
- TilingKey、边界、确定性和内存覆盖结论。
- 特性修改的新增/变化场景结果，以及未受影响场景的回归结论。
- 性能锚点、基线及相对变化，如适用。
- 优化任务的 profiling 口径、瓶颈变化、目标收益和泛化性能变化。
- 未执行项、原因、影响和后续计划。

退出本阶段前，接口、CPU 标杆、设计、实现和测试结果必须一致；所有必测项已闭环，公共改动已逐一验证全部受影响算子。公开说明只写测试项和结果，不写机器、账号、绝对路径、临时目录或日志位置。
