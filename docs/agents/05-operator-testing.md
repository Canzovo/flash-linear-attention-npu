# 算子测试

本阶段以已确认接口、CPU 标杆和算子设计为依据，验证当前实现的功能、精度、边界、确定性、内存和性能符合交付要求。具体构建、安装和 ATK 命令分别以 `docs/开发者指南.md`、`tests/atk/README.md` 和当前算子的 ATK README 为准。

## 阶段输入

- 已确认的接口契约、支持范围和异常行为。
- 已完成参考实现对齐或用户验收的独立 CPU 标杆、输入生成和比较标准。
- 归档在算子目录且整体评审通过的完整设计文档，以及 host tiling 能够选择到的 TilingKey、风险和验证计划。
- 当前实现、目标分支 diff 和受影响文件列表。
- 接口或功能修改任务还需要确认的差异清单、修改前行为和既有场景回归范围。
- 优化任务还需要优化前性能数据、profiling 方法、目标 shape 和预期收益。

CPU 标杆提供精度预期结果；接口、边界、确定性、内存、性能和端到端能力分别使用对应的测试验证。

## 验证原则

- 按改动风险选择验证范围，并分别记录编译、功能、精度和性能测试的执行结果。
- 测试覆盖语义路径、调度路径、值域路径和默认 shape 之外的代表性场景。
- 当前代码、测试文件、CPU 标杆和构建结果来自同一提交或明确对应的版本，并使用这一组内容形成测试结论。
- 仓内 ATK 自测试与 GitHub NPU CI 分别执行并满足各自的通过条件。

## 从改动确定测试范围

开始验证前，根据受影响文件按下表确定最低测试范围。

| 改动类型 | 最低验证范围 |
| --- | --- |
| 文档-only | 格式、相对链接、命令与当前脚本、文档与代码语义一致性 |
| 测试或 CPU 标杆-only | 语法/导入、CPU 标杆对齐或验收，并实际执行被修改的测试入口 |
| 算子接口或功能修改 | 新增或变化场景的精度、边界和异常验证，以及未受影响既有场景的回归测试 |
| 算子私有 op_host、tiling、kernel、op_api 或 wrapper | 当前算子的构建、CPU 标杆精度，以及对应的边界和异常输入场景 |
| TilingKey、模板选择或运行时分支 | host tiling 能够选择到的全部 key、普通/边界用例和实际选择记录 |
| 性能策略、流水或资源规划 | 精度、确定性、内存检查、目标性能，以及其他支持场景的性能 |
| 公共组件、ABI、代码生成模板或 runtime | 所有受影响算子的对应测试，以及直接覆盖被修改公共逻辑的测试 |
| 公开接口、打包或安装行为 | ABI、公开入口、重复安装、OPP 内容和必要 Example/ST |
| GDN 端到端链路 | 受影响单算子测试和 Example/ST |

公共改动沿引用、代码生成和调用关系分析，最终列出所有受影响算子及其必测项；无法确认的部分要说明分析依据、缺少的信息和可能风险。

## 测试文件

已有 ATK 工程的算子应同步维护：

- 算子 ATK README 和支持场景覆盖矩阵。
- `<op>.yaml` 和 `gen_<op>.py`。
- 已评审的 `atk_<op>.json`。
- `executor_<op>.py` 及其 CPU 标杆调用。
- 性能、确定性、mssanitizer 用例和 TilingKey 覆盖矩阵。

新增算子在交付前具备上述 ATK 文件。测试文件中要能查到 CPU 标杆接口、输入生成方式、比较范围和阈值依据；工具、目录和参数说明统一在 `tests/atk/README.md` 维护。

## 自测试流程

### 1. 快速开发迭代

1. 确认当前 CPU 标杆版本；仅在 `02` 已确认需要变化时更新 CPU 标杆，并同步必要用例和覆盖矩阵。
2. 先运行 CPU 标杆自身测试；存在 GPU 或 Triton Ascend 参考实现时，确认代表性用例仍然对齐；用户直接提供 CPU 标杆时，确认其验收用例仍然通过。
3. 按目标 SoC 构建并安装当前代码，确认运行时加载的是本轮构建结果。
4. 对每个受影响算子执行 ATK 精度测试。
5. 当前代码、CPU 标杆、测试用例和构建结果全部通过后，这一轮结果才可以作为后续开发或性能比较的依据。

精度通过后再使用该版本的性能数据形成优化结论；此前优先定位并修复精度根因。

### 2. 正式验收

选定一个精度通过版本后，固定代码、CPU 标杆、测试文件和构建结果：

1. 运行 ATK `all`，完成精度、确定性和 mssanitizer。
2. 性能相关改动单独运行 `performance`，记录目标 shape 或指定性能用例相对优化前数据的变化。
3. 根据改动范围和风险补充 ctypes ABI、公开入口、多卡、autograd、Example/ST、多 SoC 和 NPU CI。

## 接口或功能修改验收

- 对每个确认的特性差异增加正常、边界和必要的异常用例，并验证接口、输出和异常行为符合新契约。
- 对差异清单中保持不变的接口、CPU 标杆结果和既有支持场景执行回归，确认修改前后的结果一致。
- 修改公共组件、ABI、生成模板或 runtime 时，逐一测试全部受影响算子。
- 测试发现实现需要改变尚待确认的语义或支持范围时返回 `01`；发现 CPU 标杆或预期结果需要变化时返回 `02`，测试标准始终采用对应阶段确认的最新版本。

## 优化回归

优化版本只有在功能和精度保持不变后，才能形成性能结论：

- 使用相同的目标 SoC、shape、输入、构建方式、profiling 方法和统计方式比较优化前后结果。
- 先完成 CPU 标杆精度、边界、确定性和内存检查，再记录性能数据。
- 除目标 shape 外，还要覆盖设计中其他支持的 shape、dtype、layout、全部受影响 TilingKey 和支持 SoC，确认目标收益与整体功能、精度和性能同时满足要求。
- 对 workspace、同步、stage 或流水改动，补充连续多 task、slot 复用、tail、varlen 和空任务等相关场景。
- 报告目标场景性能、其他支持场景性能、资源变化和相对优化前数据的差异；结果低于预期时，继续保留优化前数据和相同测试条件，并记录实际结果。
- 若测试发现公开接口、数学语义、支持范围或 CPU 标杆必须改变，停止优化验收并重新归类任务。

## 测试矩阵

按接口契约和设计选择适用维度：

- fixed length 和 varlen；varlen 覆盖短序列、尾 chunk、多 chunk 及对应的 `cu_seqlens`、`chunk_indices` 等元数据。
- 一一对应和 grouped/GVA head 关系；至少覆盖 head ratio 为 1 和大于 1。
- 关键 `chunkSize`、K/V 维度、主 dtype、辅助输入 dtype 和 layout。
- 可选输入存在/缺失、初始/最终状态和预留参数的当前处理方式。
- 普通块、边界块、partial chunk、padding、无效区和极端值域。
- 单 task 与同一 core 连续多 task，触发 workspace slot 复用和同步协议。
- 目标 SoC 以及公共逻辑涉及的其他支持 SoC。

正常用例的预期结果来自 CPU 标杆。异常用例验证接口契约规定的 host 校验、错误类型和返回码。

## TilingKey 覆盖

新增或修改 TilingKey、模板选择条件或 tiling 分支时，从 host tiling、模板注册和 kernel 分派代码列出 host tiling 能够选择到的全部 key。当前算子的 ATK README 应维护：

| TilingKey | 选择条件 | 普通用例 | 边界用例 | 目标 SoC | 实际选择记录 |
| --- | --- | --- | --- | --- | --- |
| `<key>` | dtype、layout、shape、属性和平台条件 | ATK 用例 | ATK 用例 | A2/A3/A5 | host tiling UT 或运行时记录 |

每个 host tiling 能够选择到的 key 都需要普通和边界用例，同一 key 内的运行时分支也要覆盖。输入 shape 用于说明预期选择，host tiling UT 或运行记录用于确认实际选择。支持范围之外的组合使用 host 校验和异常用例验证。

## 失败定位

- 固定行、chunk、head 的块状错位，整片符号/幅值异常或维度映射错误：优先检查索引、layout、任务分配、搬运和写回。
- 误差集中在 padding 或无效区：核对接口契约、CPU 标杆和测试屏蔽范围。
- 同一输入多次结果不一致：优先检查 workspace 重叠、pipe event、cross-core flag 和生命周期。
- 随机数值误差：固定 shape、layout、属性和结构数据后进行多轮测试，比较误差分布，判断 NPU 实现是否持续比参考实现或 CPU 标杆误差更大。
- CPU 标杆与用户提供的参考实现存在差异：返回标杆生成阶段确认差异原因和最终预期结果，随后使用确认后的 CPU 标杆验证 NPU 实现。

定位问题时保持已确认的输入范围、失败用例、测试次数和精度阈值不变，并通过修复实现中的根本原因使测试通过。

## 结果记录与完成条件

测试结论至少包含：

- 受影响算子和选择该范围的依据。
- CPU 标杆版本、参考实现对齐结果、用户是否已确认该 CPU 标杆，以及测试文件版本。
- 目标 SoC、测试层级、执行项和结果。
- 精度用例总数、失败数和必要的错误分类。
- TilingKey、边界、确定性和内存覆盖结论。
- 接口或功能修改的新增/变化场景结果，以及未受影响场景的回归结论。
- 目标性能用例、优化前数据及相对变化，如适用。
- 优化任务的 profiling 方法和统计方式、瓶颈变化、目标收益和其他支持场景的性能变化。

本阶段完成前，接口、CPU 标杆、设计、实现和测试结果必须一致；所有必测项均已执行并通过，公共改动涉及的每个算子均已完成对应测试。
