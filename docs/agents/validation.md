# 算子验证方法

本文定义算子改动需要证明什么、如何确定测试范围，以及 Agent 自测试何时可以结束。具体构建、安装和 ATK 命令分别以 `docs/开发者指南.md`、`tests/atk/README.md` 和当前算子的 ATK README 为准。

## 验证原则

- 按改动风险选择验证范围，不把“能编译”当作“功能正确”。
- 测试必须覆盖语义路径、调度路径和值域路径，而不是只覆盖默认 shape。
- 当前代码、当前测试资产和当前构建产物必须对应，不能复用旧包或旧输出形成结论。
- 已执行、未执行和失败的验证分别记录；未执行项必须说明原因和剩余风险。
- 仓内 ATK 自测试与 GitHub NPU CI 是独立门禁，不能互相替代。

## 从改动确定测试范围

开始验证前，以目标分支与当前 `HEAD` 的 diff 列出受影响文件，再按下表确定测试范围。

| 改动类型 | 最低验证范围 |
| --- | --- |
| 文档-only | 格式、相对链接、命令与当前脚本、文档与代码语义一致性 |
| 测试-only | 语法/导入检查，并实际执行被修改的测试入口 |
| 算子私有 op_host、tiling、kernel、op_api 或 wrapper | 当前算子的构建、ATK 精度和对应边界/反向场景 |
| TilingKey、模板选择或运行时分支 | 全部可达 key、普通/边界 case 和实际命中证据 |
| 性能策略、流水或资源规划 | 精度、确定性、内存检查、目标性能和泛化性能 |
| 公共组件、ABI、代码生成模板或 runtime | 所有受影响算子的对应测试，以及共享路径专项测试 |
| 公开接口、打包或安装行为 | ABI、公开入口、重复安装、OPP 内容和必要 Example/ST |
| GDN 端到端链路 | 受影响单算子测试和 Example/ST |

公共改动的影响面和回归要求以根目录 `AGENTS.md` 为准。无法可靠映射时应继续分析引用关系并显式报告，不能静默跳过。

## 自测试闭环

### 1. 检查测试契约

已有 ATK 工程的算子应同步维护：

- 算子 ATK README。
- `<op>.yaml` 和 `gen_<op>.py`。
- 已评审的 `atk_<op>.json`。
- `executor_<op>.py`。
- 性能、确定性、mssanitizer 用例和 TilingKey 覆盖矩阵。

新增算子没有 ATK 工程时，应在交付前补齐上述资产。测试工具、目录和参数说明只在 `tests/atk/README.md` 维护。

### 2. 快速开发迭代

1. 更新必要用例和覆盖矩阵。
2. 按目标 SoC 构建并安装当前代码，确认运行时命中本轮产物。
3. 对每个受影响算子执行 ATK 精度测试。
4. 当前代码、当前用例和当前构建产物全部通过，才算一次有效开发迭代。

精度未通过时先定位根因，不使用该版本的性能数据推进优化结论。

### 3. 轮次验收

选定一个精度通过版本后固定代码、测试资产和构建产物：

1. 运行 ATK `all`，完成精度、确定性和 mssanitizer。
2. 性能相关改动单独运行 `performance`，记录目标锚点和相对基线变化。
3. 按风险补充 ctypes ABI、公开入口、多卡、autograd、Example/ST、多 SoC 和 NPU CI。
4. 检查没有测试输出、profiling、日志、缓存或生成物进入提交。

## 测试矩阵

按算子能力选择适用维度：

- fixed length 和 varlen；varlen 覆盖短序列、尾 chunk、多 chunk 及关联元数据。
- 一一对应和 grouped/GVA head 关系；至少覆盖 head ratio 为 1 和大于 1。
- 关键 `chunkSize`、K/V 维度、主 dtype、辅助输入 dtype 和 layout。
- 可选输入存在/缺失、初始/最终状态和预留但不支持参数。
- 普通块、边界块、partial chunk、padding、无效区和极端值域。
- 单 task 与同一 core 连续多 task，触发 workspace slot 复用和同步协议。
- 目标 SoC 以及公共逻辑涉及的其他支持 SoC。

反向和异常用例要验证明确拦截，不以 kernel 崩溃或未定义结果作为通过。

## TilingKey 覆盖

新增或修改 TilingKey、模板选择条件或 tiling 分支时，从 host tiling、模板注册和 kernel 分派代码枚举全部可达 key。当前算子的 ATK README 应维护：

| TilingKey | 选择条件 | 普通 case | 边界 case | 目标 SoC | 实际命中证据 |
| --- | --- | --- | --- | --- | --- |
| `<key>` | dtype、layout、shape、属性和平台条件 | ATK case | ATK case | A2/A3/A5 | host tiling UT 或运行时记录 |

每个可达 key 需要普通和边界 case，同一 key 内的运行时分支也要覆盖。输入 shape 只能说明预期选择；实际命中必须由 host tiling UT 或运行时证据确认。明确不支持的组合要有 host 校验和反向用例。

## 精度问题处理

- 固定行、chunk、head 的块状错位，整片符号/幅值异常或维度映射错误：优先检查索引、layout、任务分配、搬运和写回。
- 误差集中在 padding 或无效区：先确认该区域的公开语义和测试后处理。
- 同一输入多次结果不一致：优先检查 workspace 重叠、pipe event、cross-core flag 和生命周期。
- 随机数值误差：固定 shape、layout 和属性后进行多轮复检，再判断是否稳定劣于参考实现。

不得通过缩小输入范围、删除失败 case、降低覆盖强度或放宽阈值制造通过结论。

## 结果记录

测试结论至少包含：

- 受影响算子和选择该范围的依据。
- 目标 SoC、测试层级、执行项和结果。
- 精度用例总数、失败数和必要的错误分类。
- 性能锚点、基线及相对变化，如适用。
- 未执行项、原因、影响和后续计划。

公开说明只写测试项和结果，不写机器、账号、绝对路径、临时目录或日志位置。
