# 标杆生成

本阶段分析用户提供的参考资料和参考实现，并生成或验收独立、可复现的 CPU 标杆，为算子开发和精度测试提供预期结果。CPU 标杆必须实现已确认接口语义，不能调用待开发的 NPU 算子形成自验证。

## 阶段输入

- [`01-interface-confirmation.md`](01-interface-confirmation.md) 输出的已确认接口契约。
- 用户提供的固定版本参考实现、测试和示例。
- 用户直接提供的可运行 CPU 标杆及其版本、调用说明和已有测试，如适用。
- 用户提供的参考实现运行条件：可用的 GPU 服务器，或能够独立运行参考实现的 Triton Ascend 环境。
- 用户确认的本次支持范围、性能目标，以及本次明确不实现的内容。

如果接口仍有歧义，或用户提供的材料之间存在未解决冲突，返回接口确认阶段，不在 CPU 标杆中隐式选择语义。

## 分析用户提供的材料和参考实现

从代码、测试和文档中还原：

- 公式、运算顺序、中间状态和返回值语义。
- 输入输出 shape、dtype、layout、广播、分组和状态参数。
- 累加 dtype、cast 时机、归一化、缩放、数值稳定处理和算法近似。
- fixed/varlen、初始/最终状态、padding、无效区、partial chunk 和空输入行为。
- 可选输入缺失、非法属性、shape 不匹配和其他异常行为。
- 随机性、确定性要求及用户提供的参考实现自身的已知限制。

将分析结果写成“语义项 → 参考资料或实现证据 → CPU 实现方式”的映射。不能解释的分支或魔法常量必须先查清，不能原样复制后视为已理解。

## 确定 CPU 标杆来源与验收路径

根据用户提供的材料选择一条路径：

1. **用户提供 GPU 服务器**：优先在用户提供的 GPU 服务器上运行固定版本的原始 GPU 参考实现。固定输入、随机种子、dtype、layout、属性和代码版本，保存每个输入及对应输出；CPU 标杆必须读取相同输入并逐个输出对齐。
2. **只有 NPU 服务器**：如果用户提供的 Triton 代码可以通过仓库指导的 Triton Ascend 环境运行，可将它作为参考实现。必须确认实际命中独立的 Triton JIT kernel，并关闭会把 Triton 调用替换为待开发 Ascend C 算子的 adapter、monkey patch 或其他转发路径，避免用目标算子验证自身。
3. **用户直接提供 CPU 标杆**：不重复生成另一份 CPU 标杆。先确认它可以运行、与接口契约一致、不调用待开发 NPU 算子且不依赖 device 专属路径；再运行其已有测试，并补全缺失的代表性、边界和异常 case。用户明确确认该 CPU 标杆是语义和预期结果的依据时，没有 GPU 或 Triton Ascend 参考实现也可以完成验收。

原始 Triton 代码为适配 Triton Ascend 发生修改时，记录修改内容，并确认公式、计算顺序、输入输出和边界语义没有改变。记录参考代码版本、运行依赖版本、输入生成方式和输出文件的对应关系，确保结果可以复现。

GPU 或 Triton Ascend 参考实现无法运行时，可以使用用户提供的固定输入和对应预期输出完成动态对齐。既没有可运行的参考实现、固定输入输出，也没有用户确认可作为依据的 CPU 标杆时，只能进行静态分析和编写候选 CPU 实现；此时标杆生成阶段保持阻塞，不得宣称 CPU 标杆已对齐。

既有算子特性修改只更新受影响的 CPU 语义、预期结果和 case，未受影响部分保持不变。接口契约和 CPU 标杆均不需要变化时，不修改 CPU 标杆，按 `01` 的分流结论直接进入 `03`。

## 生成或验收 CPU 标杆

CPU 标杆应满足：

- **独立**：不调用目标 NPU 算子、不复用目标 kernel 输出，也不依赖 device 专属路径。
- **清晰**：优先使用直接表达公式的 PyTorch CPU 或等价实现，可读性优先于性能。
- **确定**：固定随机种子，显式处理初始化、状态和可选输入；同一输入重复执行结果一致。
- **稳定**：必要时使用更高精度累加或显式稳定算法，再按接口约定转换输出 dtype。
- **完整**：返回值数量、顺序、shape、dtype、layout 和状态语义与接口契约一致。
- **可复用**：函数边界可被单元测试、ATK executor 或其他测试资产直接调用。

CPU 标杆只用于生成预期结果和说明计算语义，不能在 NPU 算子无法处理某些输入时，转由 CPU 执行并作为正式功能。如果参考算法采用近似计算，或计算结果会因执行顺序不同而变化，必须写清 CPU 标杆的计算顺序，以及它和用户提供的参考实现是否一致、有哪些差异。

## 对齐用例

先用小而可解释的 case 对齐用户提供的参考实现和 CPU 标杆，再扩展规模。至少覆盖适用的以下场景：

- 最小合法 shape、常用 shape 和关键维度非对齐的边界 shape。
- fixed length 与 varlen，短序列、tail chunk 和多 chunk。
- head ratio 为 1 和大于 1，关键 K/V/chunk 组合。
- 可选输入存在/缺失、初始状态和最终状态开关。
- padding、无效区、partial chunk、零值、极小值和较大值。
- 明确不支持的组合和预期异常。

对每个输出分别记录比较范围、比较指标和阈值依据。无公开语义的 padding 或无效区可以在比较时屏蔽，但必须在接口契约和测试后处理中一致表达，不能为制造通过而临时修改。

## 差异处理

- 块状错位、符号或幅值系统性异常：优先检查公式、layout、索引、状态顺序和 mask 语义。
- 只有少量随机数值误差：检查累加 dtype、cast 时机、算法顺序和阈值依据。
- NaN/Inf：追踪用户提供的参考实现和 CPU 标杆中第一处非有限值，确认是否属于公开语义。
- 用户提供的参考实现无法在当前环境运行：可以先完成静态分析和 CPU 实现，但必须把未完成的动态对齐列为阶段阻塞，不得宣称参考实现已验证。

语义差异由用户或已有契约裁决。不得通过放宽阈值、缩小输入范围或删除失败 case 掩盖差异。

## 阶段输出

进入方案设计前应具备：

1. 用户提供的参考资料和参考实现分析记录，或用户提供 CPU 标杆的验收记录。
2. 独立 CPU 标杆代码及调用说明。
3. 最小对齐用例、输入生成方式和期望输出。
4. 每个输出的比较范围、指标和阈值依据。
5. 用户提供的参考实现与 CPU 标杆的对齐结果，或用户提供 CPU 标杆的验收结果。
6. 已知差异、限制和剩余风险。

CPU 标杆完成适用的参考实现对齐或用户提供 CPU 标杆的验收，且语义差异全部闭环后，进入 [`03-solution-design.md`](03-solution-design.md)。
